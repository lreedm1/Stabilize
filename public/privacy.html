Privacy and memory

What the current prototype remembers

Guest chats do not create server-side conversation memory. The current browser tab temporarily keeps only the latest assistant reply so it can be restored after a refresh or a visit to another Stabilize page. Signed-in use can retain continuity through a bounded local memory record and an OpenAI Conversation, subject to the limits below.

Guest use

When you use Stabilize without signing in, the application does not store a server-side conversation history for later sessions. To avoid losing the most recent result during ordinary navigation, the latest assistant reply and minimal display state are stored in session storage for the current browser tab for up to 24 hours. The user's prompt is not included in that tab-scoped record. It is cleared when the tab closes, when you sign out, or when the record expires. Your message still travels through Cloudflare infrastructure and, for ordinary AI replies, is processed by OpenAI through a stateless Responses request that asks OpenAI not to store the response object.

Signed-in memory

Google sign-in is optional. Stabilize associates a one-way account alias with a rolling summary, a small recent-message buffer, and one OpenAI Conversation identifier. Signed-in model turns use that Conversation to carry context between requests, while the application continues to keep a bounded local summary for routing and recovery. Stabilize does not place the Google account alias or email address in the OpenAI Conversation metadata.

The current implementation schedules the local memory and its linked OpenAI Conversation for deletion 30 days after the last stored exchange. Because deleting a Conversation object alone does not delete its items, cleanup first deletes the Conversation items and then deletes the Conversation object. If provider cleanup temporarily fails, the Durable Object retains the identifier and schedules another attempt rather than silently forgetting how to remove it.

Public feedback

Signed-in users can optionally submit feedback. Each accepted submission is committed as a separate JSON file on the public feedback-inbox branch of the Stabilize GitHub repository. The committed record contains the feedback text, category, submission time, a random feedback identifier, and a note that the submission came from Stabilize. It does not include the Google account alias, email address, IP address, browser user agent, chat history, or payment information. The one-way account alias is used temporarily in a separate Cloudflare Durable Object only to limit spam. Because the Git repository is public, feedback submitters are told not to include private or identifying information and must acknowledge that warning before submission.

Paid model choice

If you subscribe to model choice, Stripe hosts checkout and the billing portal and processes payment information under Stripe's terms. Stabilize does not receive or store complete card numbers. It stores Stripe customer and subscription identifiers, subscription status, the chosen AI model, and a monthly paid-model message count under the same one-way account alias used for signed-in continuity. Billing records may remain longer than conversation memory because they are needed to provide and manage an active or historical subscription.

What is not used for memory

The application is not designed to use IP addresses as conversation-memory identifiers. It does not request your Google email for account memory. Infrastructure providers may still process network metadata under their own terms.

Third-party processing

Cloudflare hosts the application and handles requests. Google handles optional sign-in. GitHub stores optional public feedback. Stripe handles optional checkout, subscription billing, and the customer billing portal. OpenAI processes messages used to generate replies and condensed memory. Guest AI requests ask OpenAI not to store Response objects. Signed-in continuity uses an OpenAI Conversation whose items remain with OpenAI until Stabilize's scheduled cleanup removes them. Provider processing, abuse monitoring, and operational records may still occur under the provider's terms.

Use caution with sensitive information

Do not enter passwords, authentication codes, financial account numbers, or information you do not want transmitted to the service providers involved. No internet service can promise zero risk.

Prototype status: This summary describes the intended current implementation. A production launch requires independent privacy, security, tax, payment, and legal review.
